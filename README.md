# Hackathon 组队雷达

> 黑客松现场的两个 30 秒问题：**我该找谁组队？** 和 **怎么让陌生人真的聊起来？**
> 一个零依赖的小工具，做完这两件事：生成可分享的组队名片 → 把人放进匹配池 → 随机抽两个人，**双方直接落进同一间聊天室**，带着自动生成的破冰话题和 5 分钟倒计时。

## 1. 问题定义

**给谁用：** 黑客松现场的参与者（多半在手机上）和主持人（面前有一块投影）。

**解决什么：** 活动开场那 30 分钟，所有人都知道「应该去找队友」，但实际发生的通常是三种浪费：

| 现场真实发生的 | 结果 |
| --- | --- |
| 挨个问「你是做什么的」 | 一次只能了解一个人，重复劳动 |
| 微信群刷自我介绍 | 信息流过去就没了，没人回头看 |
| 主持人喊「大家自由交流」 | 熟人抱团，社恐原地不动 |

组队雷达把这三件事压成一条链：**选头像填 30 秒生成一张名片 → 一键进匹配池 → 系统按技能互补+兴趣重合抽两个人 → 两个人自动进同一间聊天室，边聊边看 3 个具体问题。**

一句话：**它不负责让你认识所有人，它负责让你在 5 分钟内和一个人真的聊起来 —— 而且从「被抽中」到「说出第一句话」之间没有任何多余动作。**

## 2. 核心功能与流程

### 完整流程 A：从零到一局破冰（现场主流程）

1. **做名片** — 打开首页，**挑一个像素头像**（或留空用名字首字母），填昵称、一句话介绍，点技能/兴趣的预设标签（现场打字慢，点一下比输入快），点「保存并加入匹配池」。
   技能可以标 **想学 / 会用 / 熟练** 三档 —— 这一档信息是后面算「技能互补」的全部依据。保存之后这台设备就记住了「我是谁」（localStorage），后面自动进聊天室靠的就是它。
2. **拿到卡片** — 右边 Canvas 实时预览，「下载卡片 PNG」得到一张 2 倍图，或「复制分享链接」把资料编码进 URL 直接发群里。
   别人点开链接就能看到这张卡（**不需要服务端也能打开**，资料全在 URL 里，包括头像选择）。
3. **开始匹配** — 主持人在「破冰匹配」页选抽签方式、时长、同时开几组，点「开始匹配」。
4. **双方进入聊天室** — 匹配成功的那一刻：
   - 点按钮的这台机器直接跳到这一轮的聊天室；
   - 配对里的另外一个人，手机上（或大屏旁边那台设备上）会**自动落到同一间房**，不用刷新、不用点任何东西。
   聊天室左边是对话（气泡 + 时间 + 实时同步），右边是对家的资料、联系方式和为什么是你们。
5. **开口** — 3 条破冰话题就贴在输入框上方，**点一条就直接发出去**；也可以自己打字（Enter 发送，Shift+Enter 换行）。输入框上方一直显示这一轮的倒计时。
6. **投影（可选）** — 切到「大屏」页，全屏。**这一页只回答三个问题：第几轮、还有多久、手机该打开哪个地址**（还有一颗「复制这条地址」按钮，方便直接甩进群里）。它故意不显示配对清单，也没有「开一轮」按钮 —— 配完对两个人就各自进聊天室了，谁和谁配对没必要公之于众；投影前谁都能点到按钮，所以操作入口只留在主持人的「破冰匹配」页。
7. **时间到** — 倒计时归零变红、大屏和聊天室都会响一声。主持人点「结束这组」或「延长 2 分钟」，然后「开一轮」换人。结束后聊天记录还能翻，但发不了新消息了。

### 完整流程 B：只看「谁和我最搭」（个人用法）

1. 「破冰匹配」页 →「我是池子里的」选自己的名字。
2. 立刻列出**前 3 名**：按技能互补 + 兴趣重合算分，带分数条和第一条理由。
3. 直接照着名字去找人（配对卡上就有头像，现场认人快）。

### 聊天室是怎么认出「我是谁」的

现场有两种用法，同一套代码都支持：

| 场景 | 怎么认领身份 |
| --- | --- |
| 各自拿手机（推荐） | 在自己手机上填过名片，`localStorage` 里已经存了名片 ID，匹配成功后自动进房、自动就是自己那一侧 |
| 两个人挤在一块屏幕前 | 聊天页顶部有一个「我是」下拉，这一轮的两个人排在最前面，点一下就能换身份 |

没认领身份也能进房间（看得见记录、看得见对家资料），但会显示「观战模式」并且发不了消息 —— 宁可明确提示，也不要让人以为「消息发失败了」。

### 大屏为什么只留了三样东西

第一版的大屏是「配对清单 + 大号倒计时 + 开一轮/结束全部按钮」，加了聊天室之后这套设计就站不住了：

| 原来的职责 | 现在的处境 |
| --- | --- |
| 广播「谁和谁配对」 | 配完对两个人直接进聊天室，公之于众反而多余（还平白暴露了配对关系） |
| 全场共用一块倒计时表 | 聊天室头部已经有同一套服务端校准的倒计时，每个人手机上都有 |
| 主持人遥控（开一轮/结束全部） | 和「破冰匹配」页重复，而且投影前谁都能点到 |

只剩「加入地址」是别的页面替代不了的 —— 现场一个新人问「我该打开什么」，全场得有地方能答。所以这一页被砍成：**第几轮 / 还有多久 / 手机输哪个地址**，字号直接跟着视口走（倒计时最大 132px、地址最大 46px），投影上从最后一排也看得清；60 秒内整条状态栏变红。

顺带一个技术细节：倒计时和「时间到」提示音是**和大屏视图共用**的（`tick()` 扫所有 `.pair[data-ends]`，聊天室头部的倒计时也挂同一套属性）。砍大屏时这两处不能跟着删，否则聊天室的倒计时会一起哑掉 —— 所以提示音的条件是「大屏页或聊天页」而不是只有大屏。

### 三个抽签方式（都带随机，只是偏好不同）

| 模式 | 权重公式（相对本批最好的候选） | 适合 |
| --- | --- | --- |
| **智能互补**（默认） | `exp((分数 − 最高分) / 15)` | 想凑出能干活的小队 |
| **兴趣同好** | `exp((兴趣相似度 − 最高相似度) / 0.18)` | 纯聊天破冰，先做朋友 |
| **完全随机** | `1`（等概率） | 最公平，专治小圈子 |

### 别人没有的规则：优先见新人

三种模式**都**遵守同一条现场规则，分两层选人：

1. **第一层**：只在「从没搭档过」的人之间抽。破冰活动的核心目的就是见新人，只要还有没聊过的人，老搭档一次都不会被抽中（测试里跑 300 次验证：**0 次**）。
2. **第二层**：如果第一层凑不出人（例如全场所有人都互相聊过了），才放开老搭档，并按已搭档次数乘 `0.25ⁿ` 降权。**不会出现「开不出人」的死锁**。

### 破冰话题是算出来的，不是随机贴的

每条话题来自双方资料里的具体交叉点，最多 3 条，不足时用通用问题补齐。**这些话题在聊天室里是可点的按钮 —— 点一下就当作消息发出去**，专门治「被抽中了但不知道说什么」：

- 你熟练 X、对方想学 X → `先让 A 用一句话说出 X 最容易踩的坑，B 负责追问「为什么」。`
- 有共同兴趣 → `你们都对「独立游戏」感兴趣：各自说说最近一次为它花时间是什么时候？`
- 双方都会某项技能 → `聊聊各自踩过的最大一个坑，看能不能拼出共同方案。`
- 一方在找的角色另一方正好会 → `A 在找「前端」：直接问 B，这次愿不愿意一起做？`
- 都没有 → 从 6 条通用问题里按配对指纹确定性挑（同一对人每次看到的话题一致）

### 落单的人不会被静默丢弃

人数是奇数时，多出来的人拿到一张**「本轮轮空」卡**，上面写着建议（当计时员 / 去拉人进池）。

## 3. 技术实现

### 技术栈

**零依赖**是硬约束：现场网络可能连不上 npm，评委的电脑上也不该出现 `npm install` 失败。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 服务端 | Node.js 内置 `http/fs/path/os/crypto` | 单文件 `server.js`，无框架 |
| 实时同步 | SSE（Server-Sent Events） | 单向推送足够，比 WebSocket 少一层依赖和握手；聊天消息也走它，另一台设备发的话在自己这边 1 秒内出现 |
| 前端 | 原生 HTML/CSS/JS | 无构建步骤，无 CDN，断网可用 |
| 卡片渲染 | Canvas 2D 手绘 | 屏幕上看到的和下载的 PNG 是同一份绘制代码 |
| 图标 | 手写内联 SVG（`<symbol>` + `<use>`） | 24 网格、`stroke: currentColor`，不引图标库、不发额外请求 |
| 数据 | 内存 + `data/state.json`（原子写） | 重启不丢人，无需数据库；聊天记录也只落这一个文件 |

外部图片资源只有两类，都是本地文件：`public/img/`（logo、favicon、分享预览图）和 `public/avatars/`（10 张自选头像，共约 60KB）。

### 运行方式

**最快：双击启动**

| 系统 | 做法 |
| --- | --- |
| Windows | 双击 **`start.bat`** —— 自动检查 Node 版本、启动服务、打开浏览器；缺 Node 会给出明确提示和替代方案 |
| macOS / Linux | `chmod +x start.sh && ./start.sh` |

**命令行**

```bash
node server.js            # 最稳，推荐
node server.js --open     # 顺便自动打开浏览器
npm.cmd start             # Windows 上如果用 PowerShell，注意下面这条
PORT=9000 node server.js  # 指定端口（8788 被占用时会自动往后找 5 个）
DATA_DIR=/tmp/room1 node server.js   # 一台机器开多个「房间」
```

> ⚠️ **Windows 上不要用 `npm start`**：PowerShell 默认执行策略会拦下 `npm.ps1`，报「因为在此系统上禁止运行脚本」。用 `node server.js`，或者写 `npm.cmd start`。（这是实测踩到的，不是理论问题。）

**其它命令**

- 演示数据：`npm.cmd run seed` 塞 8 个带头像的假参与者，一打开就能试匹配

  > 注：`data/state.json` 里保存的**人物名片已经被清空**（`participants` / `pairs` / `messages` 都是空数组），仓库交付的是一个干净的活动状态。想立刻看到效果就跑一次 `seed`，或者在页面上点「载入演示参与者」。
- 接口自测：`npm.cmd test` —— 104 项断言，算法单测 + 真起服务端的端到端流程（含聊天室：发消息、越权拦截、未读计数、人走了消息跟着走）
- **真实浏览器 UI 验收**：`npm.cmd run ui-check` —— 起一个隔离服务端 + 一个**纯静态服务器**（模拟 GitHub Pages），再用 CDP 驱动无头 Edge/Chrome 把关键交互点一遍（点头像、加标签、存名片、开匹配、看倒计时是不是真的在走、**匹配成功后自动进聊天室并发消息**、**开第二个标签页模拟第二台手机验证实时同步**、空房间的兜底提示、**大屏只剩时钟和加入地址**、窄屏有没有溢出、静态模式下能不能自动识别并一键载入演示数据），64 项断言 + 5 张截图留档

**两个降级开关**（现场保命用）：

| 开关 | 作用 |
| --- | --- |
| `?offline=1` | 完全断开服务端，只用本机 localStorage。**直接双击 `public/index.html` 也能用**，适合网络彻底不可用 |
| `?nosse=1` | 只拉一次数据、不订阅实时推送。投屏机长时间挂着更省心 |

### 两种部署形态

#### 1. 完整版（推荐）：`node server.js`

多设备同步、大屏、持久化都在。`og:image` / `og:url` 的绝对地址由服务端按请求的 `Host` 自动注入，局域网 IP 还是域名都不用改代码。

#### 2. 纯静态版：只想发个链接给评委看，不用装任何东西

把 `public/` 目录传到 GitHub Pages / Vercel 就行 —— 仓库里已经带了 [`.github/workflows/pages.yml`](.github/workflows/pages.yml)，
推上去之后在 **Settings → Pages → Source 选 "GitHub Actions"**，它会自动：

1. 对前端文件做语法自检和关键文件存在性检查；
2. **把 `index.html` 里的 `__ORIGIN__` 替换成这个站点的真实地址**（静态托管没有服务端来注入，而爬虫不执行 JS，所以分享预览图的地址必须在发布前就写死）；
3. 把 `public/` 发布成一个公开链接。

静态版**不需要敲任何参数**：打开就自动识别出「这个地址上没有服务端」，切到单机模式，并在页面顶部说清楚什么能用、什么不能用。

| 静态版能用 | 静态版不能用 |
| --- | --- |
| 做名片、选头像、实时预览 | 多台设备共享同一个匹配池 |
| 下载卡片 PNG | 大屏实时同步（大屏只能看到本机的倒计时和地址） |
| 复制分享链接（资料编码在 URL 里，对方打开即见） | 服务端持久化（换浏览器就没了） |
| 破冰匹配 + 倒计时 + 破冰话题（**算法在前端跑，结果和带服务端时完全一致**） | **和别人真的聊起来**（没有服务端就只有一个浏览器，消息只存在本机） |
| 一键载入 8 个演示参与者，立刻看到完整效果 | |
| 聊天室界面：进房、发消息、点话题发送、认领身份（**单机自测用**） | |

> 静态版有个先天限制值得说清楚：每个访客用的是自己浏览器的 localStorage，
> 所以「匹配池」里只有你自己在这台设备上登记（或载入的演示）的人。
> 想体验真正的现场用法（多台手机 + 一块大屏），必须跑 `node server.js` —— 这也是 README 把它列为首选的原因。

**接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全量快照（含服务端时间 `now`、局域网地址 `net`、每个人的 `presence`：我在哪间房 + 几条未读） |
| GET | `/api/stream` | SSE，状态一变就推一次（聊天发消息也走这条，所以对方那台不用刷新） |
| GET | `/api/match/preview?id=` | 「谁和我最搭」：给某人算全部候选分数并排序 |
| POST | `/api/participants` | 登记/更新（同名+同联系方式视为同一人） |
| DELETE | `/api/participants/:id` | 移出匹配池（**连同他的配对和聊天记录一起清掉**，不留孤儿消息） |
| POST | `/api/match` | `{mode, count, durationSec}` → 开一轮，返回新配对 |
| GET | `/api/pairs/:id` | 单个配对 + 两个人的资料 + **完整聊天记录**（含服务端时间，用来对齐气泡时间） |
| POST | `/api/pairs/:id/messages` | `{from, text}` → 发一条消息；`from` 必须是这条配对的 a 或 b，否则 403 |
| POST | `/api/pairs/:id/read` | `{from}` → 把「我看到这里了」记到配对上，返回剩余未读 |
| POST | `/api/pairs/:id` | `{action:'extend'\|'finish'\|'cancel', minutes}` |
| POST | `/api/settings` | 改活动名/默认时长/默认模式 |
| POST | `/api/reset` | `{what:'pairs'\|'all'}`（清配对时聊天记录一起清） |

**聊天为什么不用另开一套通道**：消息落在 `state.messages` 里，发一条就 `pushState()` 一次。SSE 快照里**只带每间房的条数摘要**（`pairs[].chat = {count, at, last}`，`last` 截前 60 字），全量记录靠 `GET /api/pairs/:id` 单独拉。这样即使聊了几百条，每次推送也还是几 KB。前端发现「快照里的条数 > 手上这份的条数」就自动重拉一次并重画，不需要轮询。

**匹配度算法**（`public/lib/match.js`，**前后端共用同一份文件**）

```
技能互补 30  我会 + 你想学（双向都算，每对 10 分，封顶 30）
共同技能 10  双方都会用以上的技能，每项 5 分，封顶 10
兴趣重合 25  兴趣集合的 Jaccard 相似度 × 25
角色互补 30  「我在找的人」正好是对方擅长的（双向各 15）
新鲜度   ±   没配对过 +5；配过 n 次则 −8n（最低 −20）
             ────────────────────────────────
             合计 clamp 到 0–100
```

用 UMD 包一层，浏览器 `<script>` 和 Node `require` 都能加载。这样**前端列表里显示的匹配度，和真正配对时用的分数永远是同一个数**，不存在两边算法漂移。

抽签不是「取分数最高的前 N 名」——那样每轮结果固定、毫无惊喜。做法是**先算权重、再用轮盘赌抽**。

### 这里踩过一个大坑，值得单独说

第一版权重公式是 `0.25 + 2.75 × (分数/100)²`。看着合理，实际跑出来是这样：8 个人的池子里，它开出了两组**匹配度 5** 的人（所有维度全是 0，纯粹是"分剩下的"），而池子里明明有 80 分以上的组合。

原因：0.25 这个**地板值**乘以几十个平庸候选之后，总权重会盖过唯一的好组合。28 个候选里 27 个各拿 0.257，加起来 6.9；而最好的组合只有 2.7 —— 平庸组合**集体**赢了。

修法是两条：

1. **权重改成相对值**：`exp((分数 − 本批最高分) / 15)`。最好的候选权重恒为 1，其余按分差指数衰减。这样在稀疏池和密集池里都成立，不需要针对人数调参。
2. **把"见新人"提成硬规则**（上面说的两层选人），不再只靠软性降权。

改完之后实测（`node test/smoke.js`，数字都是断言里跑出来的）：

| 验证项 | 修复前 | 修复后 |
| --- | --- | --- |
| 智能模式 vs 纯随机，各 200 次的平均匹配度 | 18.4 : 5.0 | **42.9 : 15.0** |
| 5 人池反复开 400 轮抽到的不同组合数 | — | **10 种**（最高频占 48%，没有退化成固定搭配） |
| 8 人池开 2 组跑 400 轮的不同组合数 | — | **79 种**（最优组合占 33%，平均 40.2 分） |
| 还有新人可配时抽到老搭档的次数 | — | **0 / 300** |

## 4. 边界与风险

### 1）人少 / 人多 / 人数是奇数

- **1 个人**：`/api/match` 明确返回「匹配池不足 2 人」，不假装成功；算法层不产生配对也不报错。
- **奇数**：多出的人拿「轮空卡」，写明去当计时员或去拉人，不静默丢弃。
- **人多（>12 组）**：单次最多开 12 组，避免主持人误点一次把全场打散；想开更多就分两轮。
- **所有人都在交流中**：再点开始会返回 409 并提示「先结束上一轮」，不会把已配对的人重复排进去。
- **全场都互相聊过了**：自动放开老搭档（第二层），不会开不出人。

### 2）现场网络 / 设备不可靠

- 服务端起不来 → 前端 `fetch` 失败自动切本地模式，页面顶部明确显示「离线模式（只影响本机）」，而不是白屏或假装在线。
- 更彻底：`?offline=1` 或直接双击 `public/index.html`，此时匹配池和配对都存在 localStorage，单机也能完整走一遍流程。
- 只想要静态页：`?nosse=1` 关掉长连接。
- **手机上的坑**：局域网走的是 `http://192.168.x.x`，属于非安全上下文 —— `navigator.clipboard` 和 `navigator.share` 在这时**不存在**。所以复制功能写了 `document.execCommand` 兜底，全屏失败也会给提示而不是静默失败。

### 3）多人同时点「开始匹配」

- 服务端是单进程串行处理，且每次开轮都基于**当前**状态重新算空闲池，不会把同一个人排进两组（测试覆盖）。
- 所有客户端通过 SSE 收到同一份快照，手机上看到的和大屏上看到的是同一个状态；匹配成功后的「自动进聊天室」也是靠这份快照触发的，所以晚一点打开的手机同样会落到自己那一间房。大屏只看倒计时最大值，不参与任何操作 —— 它连按钮都没有。
- 冲突的极端情况（两个人同时点）：后一次请求会发现人已被占用并返回 409 提示，而不是覆盖前一次结果。
- **往聊天室发消息不能冒充别人**：`from` 必须在服务端的这条配对里，否则 403；没认领身份的人只能看不能发（前端会明说「观战模式」，而不是静默失败）。

### 4）数据会脏、会重复、会长大

- **重复登记**：刷新页面又填一次很常见。策略是「同名 **且** 同联系方式」才算同一人 —— 否则两个都叫「张伟」且都没填联系方式的人会被错误合并。
- **脏输入**：技能/兴趣去重（大小写、空格不敏感）、长度截断、非法等级回落到「会用」、请求体上限 64KB、JSON 解析失败返回 400 而不是崩掉。
- **头像字段是注入点**：头像 id 会被拼进 `<img src>`。所以 `normalizeProfile` 里按白名单校验（只接受 `avatar-01` 这种格式），`../../server.js`、`<img onerror=...>` 之类的值一律清空（测试覆盖 4 种坏值）。输出时再 `esc()` 一层。
- **消息正文里的 HTML 也是注入点**：`<img src=x onerror=...>` 会**原样存下来**（测试断言原样往返），但在渲染时统一走 `esc()`，所以它只会显示成一段文字。服务端不做「过滤成空」这种伪安全 —— 那既拦不住真正的攻击，又会莫名其妙吃掉正常内容（比如有人就想讨论 `<div>`）。
- **体积**：配对历史会随轮次无限增长。落盘保留全量，但 SSE 推送只带「进行中 + 最近 40 条」，避免长活动把每次推送撑到几百 KB。
- **聊天记录会攒**：单条最多 500 字、每间房最多 300 条（超了从最早的开始丢）、超过 12 小时的消息在下次启动时清掉；配对没了（清空配对记录 / 把参与人移出匹配池）对应的消息立刻删掉，不留孤儿数据。快照里只带条数摘要，全量记录按房间单独拉。
- **写坏文件**：`state.json` 用 tmp + rename 原子替换；解析失败时自动改名为 `.broken-<时间戳>` 并空跑启动，服务不会因为一个坏文件起不来。

### 5）时间、倒计时和图片加载

- 服务器和手机的时钟可能差几十秒。倒计时不用设备本地时间，而是**每次快照都带服务端 `now`**，前端算出偏移量再倒计时，保证大屏和手机显示同一秒数。聊天页的倒计时复用同一套机制。
- 浏览器不允许没有用户交互就播音，所以「时间到」的提示音只在大屏页和聊天页、且用户点过页面之后才会响；不响也不影响视觉提示（变红 + 显示「时间到」）。
- 卡片上的头像和 logo 是异步图片，第一帧可能还没加载完。策略是**先用首字母兜底图形顶上，加载完成后再重画一次**（只重画一次，不会循环），任何时候都不会出现空白头像。
- 像素画放大一律 `image-rendering: pixelated`（DOM）/ 关闭插值（Canvas），否则边缘会糊。
- **聊天页不整块重画**：消息列表按「最后一个消息 id」记账，只有真的变了才动 DOM；输入框、话题按钮这些正在操作的元素永远不重建。否则 SSE 每推一次快照就会重画一遍 —— 表现为打字打到一半丢焦点、正在选中的文字被清掉、往上翻记录被拽回底部。滚到底也只在新消息进来或本来就在底部时才做。

### 6）素材与品牌

- logo 原图是 1000×1000、带深色底和投影的 PNG。构建素材时裁掉了背景只留像素方块本体，再用 NEAREST 重采样生成 512 / 180 / 64 / 32 四个尺寸（总计不到 3KB）。
- 10 张头像原图各 1000×1000（单张最大 128KB），统一转成 256×256 后单张 3–10KB，整站图片总量约 60KB。
- 分享预览图 `public/img/og.png` 是**用无头浏览器截图 `scripts/og-source.html` 生成的**，文案改了重新跑一次脚本即可，不需要设计工具。

### 7）启动环节本身也会出问题（现场最常见的一类故障）

代码写得对，但「跑不起来」往往发生在敲命令这一步。实测踩到并处理掉的：

| 故障 | 原来会怎样 | 现在怎么处理 |
| --- | --- | --- |
| 8788 被占用（上一个窗口没关） | 直接抛 `EADDRINUSE` 一长串栈，看起来像程序坏了 | 自动往后试 5 个端口，并在横幅里打印**实际**地址 |
| 中文日志在某些终端是乱码 | 启动横幅里「手机该访问哪个地址」正好在乱码那几行 | Windows 传统 cmd 默认代码页是 936，而 Node 输出 UTF-8；检测到终端时服务端自动 `chcp 65001` |
| 用 `npm start` 报「禁止运行脚本」 | PowerShell 执行策略拦下 `npm.ps1` | 文档把 `node server.js` 作为首选，并给出 `npm.cmd` 的写法 |
| 电脑上没装 Node | 双击 `server.js` 被当成脚本文件打开，或者窗口一闪而过 | `start.bat` 明确提示去 nodejs.org 装 LTS，并给出「传静态托管 + `?offline=1`」的免安装替代方案 |
| 双击 `.bat` 之后乱码/报一堆「不是内部或外部命令」 | —— | `start.bat` 保持**纯 ASCII**：cmd 是按字节偏移读批处理的，文件里 `chcp` 切代码页会让它读错位、把中文行当命令执行。中文提示统一交给 Node 输出 |

## 5. 换作我怎么做（继续迭代）

按「投入产出比」排序：

### P0 · 扫码入场（预计 2–3 小时）
现在加入匹配池要么在手机上敲 URL，要么点群里的分享链接。现场最顺的路径是**大屏上放一个二维码**，扫一下直接进「填名片」页 —— 大屏现在已经把地址单独放大成一行了，加二维码就是在这行旁边再放一张图。
**代价**：需要一个 QR 编码器。不能引 CDN（离线约束），所以要自己写一个最小实现的二维码生成（byte 模式 + 自动版本 + 纠错 L/M，约 250 行），并单独测试纠错码字，属于「不难但必须仔细」的活。
**回报**：这是唯一能把「主持人喊大家扫码」变成 10 秒动作的功能，优先级最高。

### P1 · 房间制 + 主办方后台（预计 1 天）
现在只有一个全局匹配池、一个活动名（活动名还只有接口没有界面）。真实场景里可能同时有 3 个分会场，或者上午下午两场不同的人。
**代价**：`state` 要从单例变成 `rooms: Map<roomId, RoomState>`，SSE 要按房间隔离，前端加房间号路由和「房间不存在」的兜底；还要考虑旧数据迁移。顺手把活动名/时长做成可视化设置，而不是只有接口。
**回报**：一个工具能服务整场活动，而不用每场重启一次服务、删一次 `state.json`。

### P2 · 匹配质量反馈闭环（预计半天）
现在「匹配度」是我们自己算的，没人验证过它准不准。真正该做的是：5 分钟结束后，两边各点一下「想继续合作 / 就聊到这」，把结果记下来。
**代价**：要加数据表和反馈 UI；更重要的是**样本量小**（一场活动几十条），短期不足以调权重，所以它更像是在为下一次活动攒数据，而不是立刻优化算法。
**回报**：三轮之后可以用真实反馈校准那 5 个维度的权重，甚至把「想继续合作」变成匹配的主目标函数，而不是现在的代理指标。

### 明确不做的
- **不做账号系统**：一场活动的生命周期只有几小时，注册登录纯属劝退。（代价：没法跨活动保留名片，所以名片的分享链接和 PNG 导出才是主要出口；「我是谁」也只是一条 localStorage 记录，换设备要重新认领一次。）
- **不做通用 IM**：聊天室只服务「这一轮配对的这两个人、这一段时间」。没有好友列表、没有历史会话、没有群聊、没有图片语音 —— 时间一到房间就结束，记录随配对一起被清理（12 小时前的消息在服务端重启时会丢弃）。它要解决的是「被抽中了却开不了口」，不是取代微信。

## 开发过程中真实踩到的坑

按发现顺序，每一条都是真事：

1. **产品名被自己人读错** —— 最初叫「HackMatch」，被读成了 "HackerMath"。代码里从来没有 `HackerMath` 这个词，但**一个需要解释才不会被读错的名字就是坏名字**。已全部改为 `Hackathon 组队雷达`（JS 全局、localStorage 前缀、package 名、文档一并改掉）。教训：命名要在最差的显示条件下自测一遍，而不是在脑子里念一遍。
2. **`#pool-list` 容器根本没写进 HTML** —— `renderPool()` 一进去就 `innerHTML` 到 `null`，整个 `boot()` 中断，页面只剩顶栏和页脚。**是截图验证抓出来的**，不是靠读代码。顺手加了全局错误捕获：任何脚本报错都直接显示在页面底部（带文件名和行号），现场投影出问题时能当场定位。
3. **`Store.online` 赋值的顺序错了** —— 代码是 `applyState(await res.json())` 之后才 `Store.online = true`，导致**第一次渲染读的还是本地空池子**，页面显示「匹配池 0 人」而服务端明明有 8 个人。
4. **匹配算法开出了两组「匹配度 5」的人**（详见第 3 节末尾）—— 权重公式的地板值让几十个平庸候选的权重总和压过了唯一的好组合。改成相对分数（softmax）+ 新人优先的硬规则。
5. **测试里的伪随机函数是坏的** —— 用朴素 LCG，相邻种子的**第一个输出几乎相同**（种子 1 和 400 的首个随机数只差 1.5e-4），于是「跑 400 次看分布」实际上只抽了一次，随机性断言全部失效。换成 mulberry32 之后才看到真实分布，也才发现第 4 条那个算法问题。**绿灯必须可信，否则等于没有测试。**
6. **兴趣标签渲染成「只有 × 的空胶囊」** —— 技能存的是 `{name, level}` 对象，兴趣和「我在找」存的是纯字符串，而渲染函数一律取 `item.name`，字符串取 `.name` 就是 `undefined`。这个 bug 在**两轮静态截图里都没暴露**，因为截图从没拍到"标签已添加"的状态；是靠 CDP 驱动真实浏览器点了一遍才现形（见 `npm.cmd run ui-check`）。教训：**静态截图证明不了交互**。
7. **名片底部文字重叠** —— 画布高度用固定值估算页脚，技能多的时候联系方式盒子会压到页脚上并溢出画布。改成「先按真实绘制顺序量出正文底部，再倒推画布高度」。
8. **`auto-fill` 让卡片变窄** —— 只有 2 组配对时，`repeat(auto-fill, minmax(330px,1fr))` 会生成 4 条轨道，卡片只占左边两条、右边空一片。换成 `auto-fit` + `max-width` 才对。
9. **无头浏览器截图卡死** —— SSE 长连接让页面永远「没加载完」，`--dump-dom` 一直等。绕法是先加 `?offline=1` 开关（这本来就是现场需要的降级能力），截图时用它；顺带发现 `?nosse=1` 也是投屏场景真需要的。
10. **加了聊天之后，原来的「只带摘要」推送设计差点被推翻** —— 全量消息塞进每次 SSE 推送会让长活动越推越大。最后的做法是分层：快照只带「条数 + 最后一条（截 60 字）」，某个房间的完整记录按需单独拉（`GET /api/pairs/:id`）。前端发现「快照条数 > 本地份数」就重拉一次。既保住了推送体积，又不用轮询。
11. **`<select>` 不写 `selected` 会默认选中第一项** —— 聊天页的「我是」下拉里，没认领身份的人看到的是这一轮的第一个名字，看起来像已经认领了，实际是观战模式发不出消息。加了一个「— 我还没认领 —」占位项并给真正的那个人写 `selected` 才对。**这种 bug 只有把页面点一遍才会现形**，读代码时它完全说得通。
12. **「消息发出去了但界面上看不见」** —— 发消息成功后前端把本地那份记录清掉、等下一次 SSE 快照再重拉，而快照还没到的那一瞬间渲染出的就是空状态。两条修法都加上了：服务端返回的那条消息直接并进本地记录（自己的话立刻可见），以及重拉期间保留旧记录、绝不渲染成空。
13. **CDP 的 sessionId 不是 targetId** —— 为了验证「第二台手机」开了第二个标签页，第一版把 `Target.getTargets` 拿到的 targetId 当 sessionId 用，被回了一句 `Session with given id not found`。实测结论：页面级 WebSocket 本来就**不能**带 sessionId，只有 `Target.attachToTarget` 返回的那个才能用。顺手写了个三行的探针脚本把两种写法各试一遍才确定。
14. **UI 验收里往 localStorage 塞身份塞错了格式** —— 应用用 `JSON.parse` 读，测试写了裸字符串，于是 `JSON.parse` 抛错、被兜底成「没认领」，表现为「第二台设备死活发不出消息」。这类「测试数据格式和真实数据格式不一致」的问题是自伤，但排查时极容易被当成产品 bug。
