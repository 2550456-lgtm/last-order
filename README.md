# Hackathon 组队雷达

> 黑客松现场的两个 30 秒问题：**我该找谁组队？** 和 **怎么让陌生人真的聊起来？**
> 一个零依赖的小工具，做完这两件事：生成可分享的组队名片 → 把人放进匹配池 → 随机抽两个人聊 5 分钟，附带自动生成的破冰话题和倒计时。

## 1. 问题定义

**给谁用：** 黑客松现场的参与者（多半在手机上）和主持人（面前有一块投影）。

**解决什么：** 活动开场那 30 分钟，所有人都知道「应该去找队友」，但实际发生的通常是三种浪费：

| 现场真实发生的 | 结果 |
| --- | --- |
| 挨个问「你是做什么的」 | 一次只能了解一个人，重复劳动 |
| 微信群刷自我介绍 | 信息流过去就没了，没人回头看 |
| 主持人喊「大家自由交流」 | 熟人抱团，社恐原地不动 |

组队雷达把这三件事压成一条链：**选头像填 30 秒生成一张名片 → 一键进匹配池 → 系统按技能互补+兴趣重合抽两个人 → 给他们 5 分钟和 3 个具体问题。**

一句话：**它不负责让你认识所有人，它负责让你在 5 分钟内和一个人真的聊起来。**

## 2. 核心功能与流程

### 完整流程 A：从零到一局破冰（现场主流程）

1. **做名片** — 打开首页，**挑一个像素头像**（或留空用名字首字母），填昵称、一句话介绍，点技能/兴趣的预设标签（现场打字慢，点一下比输入快），点「保存并加入匹配池」。
   技能可以标 **想学 / 会用 / 熟练** 三档 —— 这一档信息是后面算「技能互补」的全部依据。
2. **拿到卡片** — 右边 Canvas 实时预览，「下载卡片 PNG」得到一张 2 倍图，或「复制分享链接」把资料编码进 URL 直接发群里。
   别人点开链接就能看到这张卡（**不需要服务端也能打开**，资料全在 URL 里，包括头像选择）。
3. **开始匹配** — 主持人在「破冰匹配」页选抽签方式、时长、同时开几组，点「开始匹配」。
4. **拿到结果** — 每组一张卡：两个人的头像、技能、兴趣 + **匹配度** + 为什么是你们（理由）+ **3 条具体的破冰话题** + 5 分钟倒计时。
5. **投影** — 切到「大屏」页，全屏。所有组的结果、大号倒计时、进度条、以及「手机该打开哪个地址」都在上面。
6. **时间到** — 倒计时归零变红、大屏还会响一声。主持人点「结束这组」或「延长 2 分钟」，然后「开一轮」换人。

### 完整流程 B：只看「谁和我最搭」（个人用法）

1. 「破冰匹配」页 →「我是池子里的」选自己的名字。
2. 立刻列出**前 3 名**：按技能互补 + 兴趣重合算分，带分数条和第一条理由。
3. 直接照着名字去找人（配对卡上就有头像，现场认人快）。

### 三个抽签方式（都带随机，只是偏好不同）

| 模式 | 权重公式（相对本批最好的候选） | 适合 |
| --- | --- | --- |
| **智能互补**（默认） | `exp((分数 − 最高分) / 15)` | 想凑出能干活的小队 |
| **兴趣同好** | `exp((兴趣相似度 − 最高相似度) / 0.18)` | 纯聊天破冰，先做朋友 |
| **完全随机** | `1`（等概率） | 最公平，专治小圈子 |

### 别人没有的规则：优先见新人

三种模式**都**遵守同一条现场规则，分两层选人：

1. **第一层**：只在「从没搭档过」的人之间抽。破冰活动的核心目的就是见新人，只要还有没聊过的人，老搭档一次都不会被抽中（测试里跑 300 次验证：**0 次**）。
2. **第二层**：如果第一层凑不出人（例如全场所有人都互相聊过了），才放开老搭档，并按已搭档次数乘 `0.25ⁿ` 降权。**不会出现「开不出人」的死锁**。

### 破冰话题是算出来的，不是随机贴的

每条话题来自双方资料里的具体交叉点，最多 3 条，不足时用通用问题补齐：

- 你熟练 X、对方想学 X → `先让 A 用一句话说出 X 最容易踩的坑，B 负责追问「为什么」。`
- 有共同兴趣 → `你们都对「独立游戏」感兴趣：各自说说最近一次为它花时间是什么时候？`
- 双方都会某项技能 → `聊聊各自踩过的最大一个坑，看能不能拼出共同方案。`
- 一方在找的角色另一方正好会 → `A 在找「前端」：直接问 B，这次愿不愿意一起做？`
- 都没有 → 从 6 条通用问题里按配对指纹确定性挑（同一对人每次看到的话题一致）

### 落单的人不会被静默丢弃

人数是奇数时，多出来的人拿到一张**「本轮轮空」卡**，上面写着建议（当计时员 / 去拉人进池）。

## 3. 技术实现

### 技术栈

**零依赖**是硬约束：现场网络可能连不上 npm，评委的电脑上也不该出现 `npm install` 失败。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 服务端 | Node.js 内置 `http/fs/path/os/crypto` | 单文件 `server.js`，无框架 |
| 实时同步 | SSE（Server-Sent Events） | 单向推送足够，比 WebSocket 少一层依赖和握手 |
| 前端 | 原生 HTML/CSS/JS | 无构建步骤，无 CDN，断网可用 |
| 卡片渲染 | Canvas 2D 手绘 | 屏幕上看到的和下载的 PNG 是同一份绘制代码 |
| 图标 | 手写内联 SVG（`<symbol>` + `<use>`） | 24 网格、`stroke: currentColor`，不引图标库、不发额外请求 |
| 数据 | 内存 + `data/state.json`（原子写） | 重启不丢人，无需数据库 |

外部图片资源只有两类，都是本地文件：`public/img/`（logo、favicon、分享预览图）和 `public/avatars/`（10 张自选头像，共约 60KB）。

### 运行方式

```bash
node server.js          # 或 npm start
# 本机访问 : http://localhost:8788/
# 手机访问 : http://<你的局域网IP>:8788/     (同一 WiFi)
# 大屏模式 : http://localhost:8788/#/screen
```

- 端口：`PORT=9000 node server.js`
- 数据目录：`DATA_DIR=/tmp/room1 node server.js`（一台机器开多个「房间」）
- 演示数据：`node scripts/seed.js` 塞 8 个带头像的假参与者，一打开就能试匹配
- 自测：`node test/smoke.js`（77 项断言，含算法单测 + 真起服务端的端到端流程）

**两个降级开关**（现场保命用）：

| 开关 | 作用 |
| --- | --- |
| `?offline=1` | 完全断开服务端，只用本机 localStorage。**直接双击 `public/index.html` 也能用**，适合网络彻底不可用 |
| `?nosse=1` | 只拉一次数据、不订阅实时推送。投屏机长时间挂着更省心 |

### 两种部署形态

1. **完整版**（推荐）：任何能跑 Node 的地方 —— `node server.js`。多设备同步、大屏、持久化都在。
   `og:image` / `og:url` 的绝对地址由服务端按请求的 `Host` 自动注入，换成局域网 IP 还是域名都不用改代码。
2. **纯静态版**：只把 `public/` 目录发到 GitHub Pages / Vercel 静态托管，用 `?offline=1` 或直接访问。
   名片生成、下载 PNG、分享链接、本地匹配全部可用，只是**没有跨设备同步**。
   静态托管时没有服务端做替换，需要手动把 `public/index.html` 里的 `__ORIGIN__` 改成你的域名（否则分享预览图不显示）。

### 数据 / 接口设计

**数据模型**（`data/state.json`）

```jsonc
// 参与者
{ "id": "p_ab12cd34ef", "name": "陈墨", "tagline": "做界面也做海报",
  "avatar": "avatar-02",                               // 空字符串 = 用名字首字母兜底
  "skills": [{ "name": "UI 设计", "level": "pro" }],   // level: learn|know|pro
  "interests": ["独立游戏"], "lookingFor": ["前端"],
  "contact": "wx: chenmo", "event": "黑客松现场",
  "joinedAt": "...", "updatedAt": "..." }

// 配对
{ "id": "m_9f8e7d6c5b", "aId": "p_...", "bId": "p_...",
  "score": 60,
  "dims": { "complement": 20, "shared": 5, "interest": 0, "role": 30, "novelty": 5 },
  "max":  { "complement": 30, "shared": 10, "interest": 25, "role": 30, "novelty": 5 },
  "reasons": ["郑野 会 硬件/嵌入式，何嘉 想学 —— 可以当场互相带一带"],
  "topics":  ["先让 郑野 用一句话说出 硬件/嵌入式 最容易踩的坑…"],
  "mode": "smart", "durationSec": 300, "extendedSec": 0,
  "createdAt": 1760000000000, "endsAt": 1760000300000, "status": "active" }
```

**接口**

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 全量快照（含服务端时间 `now` 与局域网地址 `net`） |
| GET | `/api/stream` | SSE，状态一变就推一次 |
| GET | `/api/match/preview?id=` | 「谁和我最搭」：给某人算全部候选分数并排序 |
| POST | `/api/participants` | 登记/更新（同名+同联系方式视为同一人） |
| DELETE | `/api/participants/:id` | 移出匹配池 |
| POST | `/api/match` | `{mode, count, durationSec}` → 开一轮，返回新配对 |
| POST | `/api/pairs/:id` | `{action:'extend'\|'finish'\|'cancel', minutes}` |
| POST | `/api/settings` | 改活动名/默认时长/默认模式 |
| POST | `/api/reset` | `{what:'pairs'\|'all'}` |

**匹配度算法**（`public/lib/match.js`，**前后端共用同一份文件**）

```
技能互补 30  我会 + 你想学（双向都算，每对 10 分，封顶 30）
共同技能 10  双方都会用以上的技能，每项 5 分，封顶 10
兴趣重合 25  兴趣集合的 Jaccard 相似度 × 25
角色互补 30  「我在找的人」正好是对方擅长的（双向各 15）
新鲜度   ±   没配对过 +5；配过 n 次则 −8n（最低 −20）
             ────────────────────────────────
             合计 clamp 到 0–100
```

用 UMD 包一层，浏览器 `<script>` 和 Node `require` 都能加载。这样**前端列表里显示的匹配度，和真正配对时用的分数永远是同一个数**，不存在两边算法漂移。

抽签不是「取分数最高的前 N 名」——那样每轮结果固定、毫无惊喜。做法是**先算权重、再用轮盘赌抽**。

### 这里踩过一个大坑，值得单独说

第一版权重公式是 `0.25 + 2.75 × (分数/100)²`。看着合理，实际跑出来是这样：8 个人的池子里，它开出了两组**匹配度 5** 的人（所有维度全是 0，纯粹是"分剩下的"），而池子里明明有 80 分以上的组合。

原因：0.25 这个**地板值**乘以几十个平庸候选之后，总权重会盖过唯一的好组合。28 个候选里 27 个各拿 0.257，加起来 6.9；而最好的组合只有 2.7 —— 平庸组合**集体**赢了。

修法是两条：

1. **权重改成相对值**：`exp((分数 − 本批最高分) / 15)`。最好的候选权重恒为 1，其余按分差指数衰减。这样在稀疏池和密集池里都成立，不需要针对人数调参。
2. **把"见新人"提成硬规则**（上面说的两层选人），不再只靠软性降权。

改完之后实测（`node test/smoke.js`，数字都是断言里跑出来的）：

| 验证项 | 修复前 | 修复后 |
| --- | --- | --- |
| 智能模式 vs 纯随机，各 200 次的平均匹配度 | 18.4 : 5.0 | **42.9 : 15.0** |
| 5 人池反复开 400 轮抽到的不同组合数 | — | **10 种**（最高频占 48%，没有退化成固定搭配） |
| 8 人池开 2 组跑 400 轮的不同组合数 | — | **79 种**（最优组合占 33%，平均 40.2 分） |
| 还有新人可配时抽到老搭档的次数 | — | **0 / 300** |

## 4. 边界与风险

### 1）人少 / 人多 / 人数是奇数

- **1 个人**：`/api/match` 明确返回「匹配池不足 2 人」，不假装成功；算法层不产生配对也不报错。
- **奇数**：多出的人拿「轮空卡」，写明去当计时员或去拉人，不静默丢弃。
- **人多（>12 组）**：单次最多开 12 组，避免主持人误点一次把全场打散；想开更多就分两轮。
- **所有人都在交流中**：再点开始会返回 409 并提示「先结束上一轮」，不会把已配对的人重复排进去。
- **全场都互相聊过了**：自动放开老搭档（第二层），不会开不出人。

### 2）现场网络 / 设备不可靠

- 服务端起不来 → 前端 `fetch` 失败自动切本地模式，页面顶部明确显示「离线模式（只影响本机）」，而不是白屏或假装在线。
- 更彻底：`?offline=1` 或直接双击 `public/index.html`，此时匹配池和配对都存在 localStorage，单机也能完整走一遍流程。
- 只想要静态页：`?nosse=1` 关掉长连接。
- **手机上的坑**：局域网走的是 `http://192.168.x.x`，属于非安全上下文 —— `navigator.clipboard` 和 `navigator.share` 在这时**不存在**。所以复制功能写了 `document.execCommand` 兜底，全屏失败也会给提示而不是静默失败。

### 3）多人同时点「开始匹配」

- 服务端是单进程串行处理，且每次开轮都基于**当前**状态重新算空闲池，不会把同一个人排进两组（测试覆盖）。
- 所有客户端通过 SSE 收到同一份快照，手机上看到的和大屏上看到的是同一个状态。
- 冲突的极端情况（两个人同时点）：后一次请求会发现人已被占用并返回 409 提示，而不是覆盖前一次结果。

### 4）数据会脏、会重复、会长大

- **重复登记**：刷新页面又填一次很常见。策略是「同名 **且** 同联系方式」才算同一人 —— 否则两个都叫「张伟」且都没填联系方式的人会被错误合并。
- **脏输入**：技能/兴趣去重（大小写、空格不敏感）、长度截断、非法等级回落到「会用」、请求体上限 64KB、JSON 解析失败返回 400 而不是崩掉。
- **头像字段是注入点**：头像 id 会被拼进 `<img src>`。所以 `normalizeProfile` 里按白名单校验（只接受 `avatar-01` 这种格式），`../../server.js`、`<img onerror=...>` 之类的值一律清空（测试覆盖 4 种坏值）。输出时再 `esc()` 一层。
- **XSS**：所有用户输入在拼进 HTML 前统一转义（`esc()`）；昵称里写 `<img onerror=…>` 不会生效。
- **体积**：配对历史会随轮次无限增长。落盘保留全量，但 SSE 推送只带「进行中 + 最近 40 条」，避免长活动把每次推送撑到几百 KB。
- **写坏文件**：`state.json` 用 tmp + rename 原子替换；解析失败时自动改名为 `.broken-<时间戳>` 并空跑启动，服务不会因为一个坏文件起不来。

### 5）时间、倒计时和图片加载

- 服务器和手机的时钟可能差几十秒。倒计时不用设备本地时间，而是**每次快照都带服务端 `now`**，前端算出偏移量再倒计时，保证大屏和手机显示同一秒数。
- 浏览器不允许没有用户交互就播音，所以「时间到」的提示音只在大屏页、且用户点过页面之后才会响；不响也不影响视觉提示（变红 + 显示「时间到」）。
- 卡片上的头像和 logo 是异步图片，第一帧可能还没加载完。策略是**先用首字母兜底图形顶上，加载完成后再重画一次**（只重画一次，不会循环），任何时候都不会出现空白头像。
- 像素画放大一律 `image-rendering: pixelated`（DOM）/ 关闭插值（Canvas），否则边缘会糊。

### 6）素材与品牌

- logo 原图是 1000×1000、带深色底和投影的 PNG。构建素材时裁掉了背景只留像素方块本体，再用 NEAREST 重采样生成 512 / 180 / 64 / 32 四个尺寸（总计不到 3KB）。
- 10 张头像原图各 1000×1000（单张最大 128KB），统一转成 256×256 后单张 3–10KB，整站图片总量约 60KB。
- 分享预览图 `public/img/og.png` 是**用无头浏览器截图 `scripts/og-source.html` 生成的**，文案改了重新跑一次脚本即可，不需要设计工具。

## 5. 换作我怎么做（继续迭代）

按「投入产出比」排序：

### P0 · 扫码入场（预计 2–3 小时）
现在加入匹配池要么在手机上敲 URL，要么点群里的分享链接。现场最顺的路径是**大屏上放一个二维码**，扫一下直接进「填名片」页。
**代价**：需要一个 QR 编码器。不能引 CDN（离线约束），所以要自己写一个最小实现的二维码生成（byte 模式 + 自动版本 + 纠错 L/M，约 250 行），并单独测试纠错码字，属于「不难但必须仔细」的活。
**回报**：这是唯一能把「主持人喊大家扫码」变成 10 秒动作的功能，优先级最高。

### P1 · 房间制 + 主办方后台（预计 1 天）
现在只有一个全局匹配池、一个活动名（活动名还只有接口没有界面）。真实场景里可能同时有 3 个分会场，或者上午下午两场不同的人。
**代价**：`state` 要从单例变成 `rooms: Map<roomId, RoomState>`，SSE 要按房间隔离，前端加房间号路由和「房间不存在」的兜底；还要考虑旧数据迁移。顺手把活动名/时长做成可视化设置，而不是只有接口。
**回报**：一个工具能服务整场活动，而不用每场重启一次服务、删一次 `state.json`。

### P2 · 匹配质量反馈闭环（预计半天）
现在「匹配度」是我们自己算的，没人验证过它准不准。真正该做的是：5 分钟结束后，两边各点一下「想继续合作 / 就聊到这」，把结果记下来。
**代价**：要加数据表和反馈 UI；更重要的是**样本量小**（一场活动几十条），短期不足以调权重，所以它更像是在为下一次活动攒数据，而不是立刻优化算法。
**回报**：三轮之后可以用真实反馈校准那 5 个维度的权重，甚至把「想继续合作」变成匹配的主目标函数，而不是现在的代理指标。

### 明确不做的
- **不做账号系统**：一场活动的生命周期只有几小时，注册登录纯属劝退。（代价：没法跨活动保留名片，所以名片的分享链接和 PNG 导出才是主要出口。）
- **不做聊天**：现场就在同一个屋子，工具的价值是「把两个人推到对方面前」，剩下的交给他们的嘴。加聊天只会让这个工具变成一个更差的微信。

## 开发过程中真实踩到的坑

1. **产品名被自己人读错** —— 最初叫「HackMatch」，被读成了 "HackerMath"。代码里从来没有 `HackerMath` 这个词，但**一个需要解释才不会被读错的名字就是坏名字**。已全部改为 `Hackathon 组队雷达`（JS 全局、localStorage 前缀、package 名、文档一并改掉）。教训：命名要在最差的显示条件下自测一遍，而不是在脑子里念一遍。
2. **`#pool-list` 容器根本没写进 HTML** —— `renderPool()` 一进去就 `innerHTML` 到 `null`，整个 `boot()` 中断，页面只剩顶栏和页脚。**是截图验证抓出来的**，不是靠读代码。顺手加了全局错误捕获：任何脚本报错都直接显示在页面底部（带文件名和行号），现场投影出问题时能当场定位。
3. **`Store.online` 赋值的顺序错了** —— 代码是 `applyState(await res.json())` 之后才 `Store.online = true`，导致**第一次渲染读的还是本地空池子**，页面显示「匹配池 0 人」而服务端明明有 8 个人。
4. **匹配算法开出了两组「匹配度 5」的人**（详见第 3 节末尾）—— 权重公式的地板值让几十个平庸候选的权重总和压过了唯一的好组合。改成相对分数（softmax）+ 新人优先的硬规则。
5. **测试里的伪随机函数是坏的** —— 用朴素 LCG，相邻种子的**第一个输出几乎相同**（种子 1 和 400 的首个随机数只差 1.5e-4），于是「跑 400 次看分布」实际上只抽了一次，随机性断言全部失效。换成 mulberry32 之后才看到真实分布，也才发现第 4 条那个算法问题。**绿灯必须可信，否则等于没有测试。**
6. **名片底部文字重叠** —— 画布高度用固定值估算页脚，技能多的时候联系方式盒子会压到页脚上并溢出画布。改成「先按真实绘制顺序量出正文底部，再倒推画布高度」。
7. **`auto-fill` 让卡片变窄** —— 只有 2 组配对时，`repeat(auto-fill, minmax(330px,1fr))` 会生成 4 条轨道，卡片只占左边两条、右边空一片。换成 `auto-fit` + `max-width` 才对。
8. **无头浏览器截图卡死** —— SSE 长连接让页面永远「没加载完」，`--dump-dom` 一直等。绕法是先加 `?offline=1` 开关（这本来就是现场需要的降级能力），截图时用它；顺带发现 `?nosse=1` 也是投屏场景真需要的。

## 项目结构

```
.
├── server.js                 # 零依赖服务端：静态托管 + JSON API + SSE + 落盘 + og 地址注入
├── public/
│   ├── index.html            # 三个视图 + 内联 SVG 图标集 + 全局错误捕获
│   ├── styles.css            # 全部样式，无外部字体/图标库
│   ├── app.js                # 前端主逻辑：路由、表单、头像选择、匹配、倒计时、离线降级
│   ├── card.js               # 名片 Canvas 渲染（预览与导出同一份代码）
│   ├── lib/match.js          # 匹配算法内核，前后端共用（UMD）
│   ├── img/                  # logo.png / favicon.png / logo-180.png / og.png（分享预览图）
│   └── avatars/              # 10 张自选像素头像，256×256
├── test/smoke.js             # 77 项断言：算法单测 + 端到端
├── scripts/
│   ├── seed.js               # 演示数据（8 人，带头像）
│   ├── og-source.html        # 分享预览图的源文件，用无头浏览器截成 img/og.png
│   └── shot.ps1              # 开发期截图助手（Windows + Edge，用来逐视图肉眼验证）
├── Images/                   # 原始素材（1000×1000，未压缩，不进仓库）
└── data/state.json           # 运行时数据（已 gitignore）
```

**替换素材**：logo 换掉后按同样方式裁切并重新生成各尺寸；头像按 `public/avatars/avatar-01.png … avatar-10.png` 命名放进去即可（`app.js` 顶部的 `AVATARS` 数组决定可选范围）。分享预览图改文案后重新截 `scripts/og-source.html`。

> 页面改动是**用截图逐视图验证**的，不是只跑测试。这个习惯当场抓出了两个测试测不到的 bug（第 2、3 条）。
