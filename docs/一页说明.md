**用法：AI 承担全部代码实现，我承担需求定义、方案决策与验收。**

| 阶段 | AI 做了什么 | 我做了什么 |
| --- | --- | --- |
| 需求 | 拆解题目、给出三个可行方向 | 选定方向，提出两条硬约束：**不使用任何图片素材**、**先出无图预览版** |
| 架构 | 提出「零依赖 Node + 原生前端 + 前后端共用一份匹配算法」的结构 | 确认取舍：接受"没有构建步骤"换来"断网可用" |
| 编码 | 编写全部代码（服务端、前端、算法、测试、脚本） | 逐轮给方向性反馈，控制范围（先不做投票墙等） |
| 验证 | 写 61 项断言、用无头浏览器给每个视图截图 | 确认"能跑起来"的验收标准 = 截图里真的看到内容 |
| 文档 | 起草 README 与本文档 | 复核事实与口径 |

**AI 帮我省掉的**：样板代码、边界情况的穷举、测试用例的铺开、重复的调试循环。

**AI 没能替我做的**（也是我认为使用 AI 时最该自己盯的部分）：

1. **判断"看起来对"和"真的对"的差距**。页面首次截图是**空的**——AI 写的代码语法正确、测试全绿，但主内容区一片空白。原因是 HTML 里少了一个 `#pool-list` 容器，JS 一进去就抛错中断了 `boot()`。自动化测试测的是 API，测不到"页面有没有东西"。这条只能靠人盯着截图发现。
2. **拒绝假绿灯**。测试里有一条断言时好时坏，因为它依赖真随机。AI 的第一反应是放宽断言；正确做法是承认**测试本身写错了**，改成注入固定种子做统计验证。绿灯必须可信，否则等于没有测试。
3. **产品口径**。比如"匹配度 5 分"要不要显示？AI 倾向于美化数字，我选择如实显示——因为随机模式本来就不承诺契合度，配套加了"抽签抽中的，分数仅供参考"的说明。

## 三、最大的困难与解决方式

### 困难：「随机匹配」这件事，纯随机和纯最优都是错的

题目要求是"**随机**匹配两人"。但真做下去会发现两个方向都不可用：

- **纯随机**（等概率抽两个人）：现场 8 个人里可能有 4 个都是前端、2 个都只会 Python——抽出来的组合大概率聊不出任何东西，"破冰"变成"尬聊 5 分钟"。
- **纯最优**（永远把分数最高的两个人凑一起）：第一轮效果最好，第二轮还是那两个人，第三轮依然是——因为配对结果从资料算出来就是**确定的**。现场会立刻发现规律，工具失去意义，还会造成小圈子固化。

**真正要的是**：结果有意义（大概率是好组合），但**不可预测**（每轮不一样，谁都可能遇到谁）。

### 解决方式：把分数当权重，而不是当排名

分三步：

1. **先定义"什么叫搭"**，拆成 5 个可计算、可解释的维度（技能互补 30 / 共同技能 10 / 兴趣重合 25 / 角色互补 30 / 新鲜度 ±）。每一项都能翻译成一句人话，直接显示给参与者看——**如果算出来的理由说不出口，这个维度就是错的**。
2. **分数不排序，转成权重再用轮盘赌抽**：分数高的人被抽中的概率大，但低分组合仍有概率被抽到。这样既保留了"随机"的字面要求，又让结果倾向于有意义。三种模式只是把分数映射成权重的公式不同。
3. **对老搭档乘一个 0.25ⁿ 的降权因子**（n 是已搭档次数）：明显避开，但不硬性排除——人少的时候照样能配上，不会出现"没人可配"。

### 怎么证明它真的解决了

不靠感觉，靠统计断言：

| 验证项 | 结果 |
| --- | --- |
| 智能模式 vs 纯随机，各跑 200 次取平均分 | **18.4 : 5.0** —— 智能模式确实在挑更搭的人 |
| 3 人池中让一对"老搭档"参与抽签 300 次 | 被重复抽中 **39 次**（均等概率应为 100 次）—— 降权生效，但不是排除 |
| 同一种子两次抽签结果 | **完全一致** —— "随机"依然可复现、可测试 |

### 从这件事上学到的

**"随机"不是一个功能，是一个需要被设计的产品参数。** 当需求里出现"随机"两个字时，真正要问的是：它需要多随机？哪些结果应该更容易出现？哪些组合应该被避免？把这些问题答清楚，代码其实只有几十行；答不清楚，写再多也是碰运气。

## 四、如果只能再改一处

**加大屏二维码入场。** 现在加入匹配池要手敲 URL，这是整条链路上唯一一个"不够 30 秒"的环节。做法是自己写一个最小二维码编码器（零依赖约束下不能用库），把当前地址编码后显示在大屏上。代价约 2–3 小时，回报是把"主持人喊大家扫码"变成 10 秒就能完成的动作。详细优先级排序见 README 第 5 节。
